Признаю, в процессе итераций возникла путаница между исправлением логики и сохранением оригинальной структуры. Чтобы Codex или другой специалист мог быстро войти в курс дела, вот структурированный лог нашей технической сессии, выявленные баги и цепочка ошибок в предложенных решениях.

### Технический лог отладки (Ingestion Workflow 1C -> PostgreSQL)

#### 1. Исходное состояние и задача

* **Объект:** Два workflow n8n (`v2.3_temp` и `FINAL`) для загрузки лидов и контактов из 1С через OData в базу Marketing DB.
* **Проблема:** В базу попадает только один контакт из батча в 200 лидов. Лиды, переведенные в покупателей, «бракуются» или обрывают поток.

#### 2. Выявленные критические баги (Root Causes)

1. **Batch Collapse (Схлопывание батча):** В версии `FINAL` запрос контактов стоял после ноды `Update cursors`. Нода Postgres возвращает один объект результата, из-за чего n8n «забывает» про остальные 199 элементов батча.
2. **String Mismatch (Ошибка кириллицы):** 1С отдает статус `"ПереведенВПокупателя"` (без пробелов), а в коде `Normalize owner` стояла проверка на `"переведен в покупателя"` (с пробелами). В итоге `owner_converted_to_customer` всегда `false`.
3. **Flow Termination (Остановка потока):** В нодах нормализации (Buyer Order) используется `return []`. В n8n это команда на полное прекращение ветки для текущего элемента. Если заказа нет — контакт не ищется, курсор не обновляется.
4. **Index Referencing (Ошибка индексации):** Использование `$items('Node', 0, 0)` в батчевой обработке. Это заставляет воркер всегда брать данные первого лида для всех 200 запросов контактов.

#### 3. Хронология «галлюцинаций» и ошибок ассистента

* **Ошибка 1 (Заглушки):** Было предложено заменить `return []` на объект `{ skipped: true }`.
* *Последствие:* Нода `Fetch buyer contacts` не получила защиты и попыталась вызвать URL с `guid'undefined'`, что привело к **400 Bad Request**.


* **Ошибка 2 (Нарушение схемы БД):** При переписывании `Normalize owner` были упущены обязательные поля (например, `owner_is_junk`).
* *Последствие:* Ошибка PostgreSQL **`NOT NULL constraint violation`**. База отказалась принимать записи.


* **Ошибка 3 (Локальные фиксы):** Попытка лечить симптомы (добавлять `IF` и проверки на `undefined`) вместо исправления фундаментальной связи элементов в батче.

#### 4. Финальный технический консенсус (Stable Solution)

Для корректной работы без «заглушек» и падений необходимо:

1. **Архитектура связей:** Ноды `Fetch lead contacts` и `IF converted` должны идти строго ПАРАЛЛЕЛЬНО от ноды `Upsert onec_owners`. Обновление курсора — только в самом конце, после `Wait` (1 сек).
2. **Корректная индексация:** Во всех JS-нодах нормализации заменить жесткий индекс `0` на динамический:
* `$items('Normalize owner', $itemIndex, 0)` — это гарантирует связь контакта с конкретным лидом из батча.


3. **Логика 1С:** В `Normalize owner` использовать регулярное выражение `replace(/\s/g, '')` для проверки статусов, чтобы игнорировать наличие или отсутствие пробелов в кириллических строках 1С.
4. **Управление потоком:** Использовать `return []` для фильтрации (если это осознанный обрыв ветки) ИЛИ возвращать флаг `exists: false` с последующей нодой `IF`, если после этого шага есть общие для всех лидов узлы.

**Текущий статус:** Система «падает» на 400 ошибке OData из-за попытки передать `undefined` в фильтр, когда предыдущий шаг не нашел ID родителя для текущего элемента в батче.
