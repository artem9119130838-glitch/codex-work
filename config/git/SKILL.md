# Навык: Git Workflow и хуки безопасности

Этот навык предназначен для защиты исходного кода и настроек репозиториев на локальной машине разработчика.

## 1. Настройка pre-push защиты репозиториев

Для исключения случайного пуша личных файлов или секретов в публичные репозитории на локальной машине используется глобальный pre-push хук.

### Схема работы:
1. Вайтлист разрешенных путей к удаленным репозиториям хранится в файле:
   `C:/codex_home/.git_hooks/allowed_remotes.json`
2. Скрипт хука `/C:/codex_home/.git_hooks/pre-push` читает этот файл и сопоставляет URL удаленного репозитория.
3. Если совпадений не обнаружено, пуш прерывается с ошибкой, если только не задана переменная обхода:
   `ALLOW_EXTERNAL_PUSH=1`

### Редактирование списка разрешенных репозиториев:
Чтобы разрешить пуш в новый репозиторий, откройте [allowed_remotes.json](file:///C:/codex_home/.git_hooks/allowed_remotes.json) и добавьте шаблон в массив `"allowed"` (поддерживается маска `*`).

> [!IMPORTANT]
> Обращайте внимание на формат протокола подключения (SSH или HTTPS):
> * Для HTTPS-адресов используйте слэш: `"github.com/account/*"`
> * Для SSH-адресов используйте двоеточие: `"github.com:account/*"`
> Рекомендуется добавлять оба варианта для беспрепятственного пуша.

```json
{
  "allowed": [
    "github.com/wlissespanchame370-cyber/*",
    "github.com:wlissespanchame370-cyber/*"
  ]
}
```

## 2. Изоляция коммитов (User Identity)

В общем командном контуре (`C:\Codex_Shared`) репозитории проектов должны иметь локальные настройки автора, не совпадающие с вашими личными данными (email/имя).

### Проверка текущих настроек репозитория:
```bash
git config user.name
git config user.email
```

### Задание локальных подставных настроек автора (в папке проекта):
```bash
git config --local user.name "wlissespanchame370-cyber"
git config --local user.email "wlissespanchame370-cyber@users.noreply.github.com"
```
*Это предотвратит связывание ваших личных GitHub-аккаунтов с рабочими коммитами.*

## 3. Решение конфликта пуша при обнаружении больших файлов (>100MB)

Если GitHub отклоняет пуш с ошибкой `pre-receive hook declined` из-за тяжелых файлов (например, выгрузок конфигураций `.cf`, логов чатов `.html` или архивов `.zip`), которые случайно попали в историю неотправленных локальных коммитов, используйте безопасный обход без удаления файлов:

1. **Сбросьте локальные коммиты до состояния origin/master**, сохранив все измененные файлы как готовые к коммиту (staged):
   ```bash
   git reset --soft origin/master
   ```
2. **Исключите тяжелые файлы из отслеживания Git** (они будут удалены из индекса коммита, но физически останутся на диске):
   ```bash
   git rm --cached "path/to/large_file"
   ```
3. **Добавьте файлы в локальный игнор-лист репозитория**, чтобы Git их больше не замечал:
   Откройте `.git/info/exclude` (или `.gitignore`) и добавьте туда относительный путь к файлу.
4. **Сделайте новый чистый коммит** и отправьте его на GitHub:
   ```bash
   git commit -m "clean commit description"
   git push origin master
   ```

## 4. Использование абсолютных путей для кастомных SSH-ключей в git config

При настройке индивидуального SSH-ключа для конкретного репозитория через параметр `sshCommand` в файле `.git/config` (или глобальную переменную `core.sshCommand`), обязательно указывайте **абсолютный путь** к файлу ключа на диске.

* **Неправильно (относительный путь)**:
  `sshCommand = ssh -i id_project_key -o StrictHostKeyChecking=no`
  *Приведет к ошибке `Identity file not accessible` и `Permission denied (publickey)`, если команда запускается из другого каталога или фоновым процессом.*

* **Правильно (абсолютный путь)**:
  `sshCommand = ssh -i C:/Users/Артем/.ssh/id_project_key -o StrictHostKeyChecking=no`

## 5. Решение конфликтов учетных записей при наличии нескольких SSH-ключей на Windows

Если на локальной машине настроено несколько SSH-ключей для разных аккаунтов GitHub (например, личный и рабочий), команда `git push` может завершаться ошибкой `Permission denied (publickey)` из-за того, что Git по умолчанию использует дефолтный системный ключ. Также алиасы хостов в `~/.ssh/config` (например, `wlisses.github.com`) могут не разрешаться Git-клиентом на Windows (вызывая ошибку `Name or service not known`).

### Решение (форсированный пуш с явным указанием приватного ключа):
Если попытки пуша стандартным способом не удаются, используйте временное переопределение команды SSH с абсолютным путем к нужному ключу:

```bash
git -c core.sshCommand="ssh -i <абсолютный_путь_к_файлу_ключа> -p 443 -o StrictHostKeyChecking=no" push
```

*Пример для рабочей среды:*
```bash
git -c core.sshCommand="ssh -i C:/Users/Артем/.ssh/id_ed25519_wlisses -p 443 -o StrictHostKeyChecking=no" push
```

Этот способ обходит любые проблемы с неразрешимыми алиасами хостов в конфигурационном файле SSH и гарантированно авторизует коммиты под правильным аккаунтом.

## 6. Защита секретов инфраструктуры и дампов устройств

Реестры инфраструктурных данных (например, `registry.json`, `INFRASTRUCTURE.md`) и локальные бэкапы конфигураций сетевых устройств (например, дампы роутеров Keenetic) содержат конфиденциальные данные и пароли. 

* **Правило**: Перед созданием коммитов всегда проверять статус этих файлов (`git status`). 
* **Действие**: Они должны быть строго добавлены в локальный `.gitignore` или `.git/info/exclude` репозитория для предотвращения случайной утечки (L5-риск).
