# Общие правила работы и TOKEN-FIRST (Личный контур)

Этот файл определяет правила оптимизации расхода токенов API и стандарты кодирования.

## 1. TOKEN-FIRST Регламент (Экономия контекста)

Перед чтением файлов или поиском ИИ обязан следовать цепочке принятия решений:
1. **Оценка необходимости**: Если на вопрос можно ответить по контексту или памяти — чтение файлов запрещено.
2. **Анализ индекса**: Перед открытием любого файла крупнее **250 строк** сверяться с `.ai/file_index.json`.
3. **Порционное чтение**: Запрещено считывать файл целиком, если нужен только фрагмент. Использовать `view_file` с указанием диапазона строк (не более 200 строк за один раз).
4. **Лимит сессии**: При достижении 10–12 шагов в чате предупредить пользователя о необходимости сжатия сессии (`py scripts/session_compress.py`).

## 2. Стандарты экономии вывода (Output Economy)
1. **Запрет на дублирование кода**: Категорически запрещено выводить в чат или в планы изменений файлы кода целиком. Показывать изменения исключительно в виде компактных diff-блоков (измененные строки + 2-3 строки контекста) или точечными фрагментами.
2. **Сухой технический ответ**: Форматировать ответы предельно лаконично. Исключить вежливые приветствия, пересказы вопросов пользователя и разжевывание очевидного. Использовать списки и таблицы вместо абзацев.
3. **Локальный поиск в приоритете**: Запрещено опрашивать удаленный сервер (SSH, curl), если нужную информацию (конфиги, версии ПО) можно найти в локальной базе знаний `codex_kb/` или в Git-логе.

## 3. Фиксация прогресса и ведение логов
* **Рабочий лог (todo.md)**: Фиксировать задачи в [todo.md](file:///C:/Codex_Personal/todo.md) (`[ ]` — не начато, `[/]` — в процессе, `[x]` — готово).
* **База знаний**: Любые изменения конфигурации серверов, портов, путей и ПО фиксировать в `codex_kb/10_assets/` или `codex_kb/progress/` с инструкцией по откату.
* **Лимиты на попытки**: Разрешено делать максимум **3 попытки** автоисправления сборки/тестов или обхода проблемы при отсутствии доступов. Если не помогло — остановиться и запросить данные у пользователя.
* **Координация задач и исполнителей**: Если задача или ее часть делегируется внешнему разработчику (например, Михаилу) или если от пользователя поступают внешние документы планирования (например, из папки Downloads), ИИ обязан явно фиксировать в `todo.md` и `.ai/SESSION_SUMMARY.md`:
  1. Ссылку на внешний источник/файл (если применимо);
  2. Имя ответственного исполнителя;
  3. Конкретный список переданных ему задач;
  4. При старте новой сессии ИИ обязан в первую очередь проверить по Git-логу, выполнены ли эти задачи исполнителем, прежде чем предлагать делать их самостоятельно.

## 4. Кодировка, секреты и стандарты разработки
* **Кодировка**: Файлы с кириллицей сохранять строго в **UTF-8 с BOM** (utf-8-sig). При чтении в PowerShell использовать `Get-Content -Encoding UTF8`.
* **Запрет на секреты**: Запрещено сохранять в репозитории пароли, API-ключи, приватные SSH/VPN ключи. Всегда использовать плейсхолдеры.
* **Принцип DRY & Изоляция**: Переиспользовать существующий код проекта. Для Python-проектов всегда создавать и использовать локальное виртуальное окружение `.venv`.
* **Запрет MVP**: Не использовать концепцию и терминологию MVP (Minimum Viable Product). Всегда делать правильно, чисто и масштабируемо с первого раза.
* **Сбои MSVC в Windows**: При ошибках отсутствия компилятора C++ (`Microsoft Visual C++ is required`) прекратить попытки и предложить Docker или Wheel.
* **Счетчики в UI**: На русском языке использовать стабильные формулировки без динамических склонений (например, "Файлов выбрано: 5").
* **Контроль запуска серверов**: Запрещено самостоятельно запускать, перезапускать или останавливать dev-сервера и фоновые службы без прямого запроса пользователя.
* **Ограничение авто-тестов**: Инструменты автоматизации браузера (Playwright, browser-use) использовать только по прямому указанию. Для мелких правок кода визуальную проверку в браузере не запускать.
* **Установка зависимостей и пакетный менеджмент**: ИИ запрещено запускать установку пакетов по одному вручную в цикле, если групповая установка падает с ошибкой. При сбое групповой установки сразу остановиться и предложить пользователю решение.
* **Разграничение записи файлов**: При создании или редактировании рабочих файлов проекта (код, скрипты, конфигурации в воркспейсе) вызывать `write_to_file` строго БЕЗ `ArtifactMetadata`. Метаданные `ArtifactMetadata` передавать исключительно при создании официальных артефактов в специальной папке разговора.
* **Ограничение grep_search**: Запрещено использовать инструмент `grep_search` на хосте Windows, если Git отсутствует в глобальном PATH среды выполнения. Вместо этого осуществлять поиск по тексту средствами PowerShell (`Select-String`).
* **Форматирование PowerShell скриптов**: Избегать написания сверхдлинных однострочных цепочек команд в PowerShell. Для снижения рисков обрезки строк или ошибок парсинга разделять логику на переменные или использовать скрипты с явными переносами строк.
* **Деплой в Docker (Обход геоблока)**: При развертывании контейнеров в bridge-режиме (FastAPI, n8n и др.), обращающихся к Gemini API из РФ, обязательно прописывать директиву `extra_hosts` с маппингом `"generativelanguage.googleapis.com:87.228.47.204"`. Контейнеры по умолчанию не наследуют `/etc/hosts` хоста.
* **Самодиагностика сервисов (Healthchecks)**: При разработке бэкап/RAG-сервисов и API обязательно реализовывать внутренний эндпоинт проверки здоровья `/health` (или `/verify`), который тестирует доступность зависимостей (соединение с СУБД, валидность API-ключей Gemini и доступность Bitrix24 Proxy).
* **Защита реестров в Git**: Файлы единого реестра инфраструктуры (`infrastructure_registry/`) и дампы конфигураций сетевого оборудования (папка `clients configs/`) содержат критические пароли и WireGuard-ключи. Они должны быть строго внесены в `.gitignore` монорепозитория.
