## 2. Анатомия аварии со сжиганием баланса DeepSeek

### 2.1. Исходные факты инцидента
* **Период сжигания:** с 03 по 09 октября 2026 г.
* **Момент обнаружения:** 10 октября 2026 г. при падении запросов с ошибкой `HTTP 402 Insufficient Balance`.
* **Виновник:** Фоновый cron-скрипт `run_summaries_batch.py` в сервисе `email_ai` (контейнер `onec_sync_daemon` на сервере `109.248.170.181`).
* **Исключенный ложный след:** Тендерный сервис Михаила (`tender-rag-api`) был проверен аппаратно — его суммарный расход за все время составил всего **$0.033 (~3 рубля)**.
* **Масштаб потерь:** 3 055 вызовов DeepSeek, 37.5 млн токенов, ~$12.11 (~1 200 руб.).

### 2.2. Механизм ловушки
1. **Безостановочный крон:** `run_summaries_batch.py` запускался **каждый час (24 раза в сутки)** пачками по 100 писем для суммаризации истории переписки клиентов и компаний.
2. **Бесшовный автоматический Failover:** Бесплатные модели Google Gemini (`gemini-3.5-flash`, `gemini-2.5-flash`) периодически ловили лимиты `429 (ResourceExhausted)` или `503`. Сервис автоматически и бесшумно переключался на резервный контур DeepSeek (`deepseek-chat`).
3. **Отсутствие дифференциации задач:** Платный DeepSeek использовался для рутинной фоновой суммаризации старой почты для каждого письма подряд точно так же, как и бесплатный Gemini.
4. **Завышенный суточный лимит:** В кодовой базе стоял дневной лимит в **500 вызовов в сутки**, который скрипт методично сжигал изо дня в день.
5. **Маскировка в дашбордах:** Из-за рассинхронизации колонок `cost_usd` в Metabase отображался ноль, что создавало иллюзию бесплатной работы.

## 3. Скрытые ловушки в коде: счетчик в файле и циклический перебор

При детальном анализе кодовой базы были обнаружены три архитектурные ловушки, которые могли повторно привести к сжиганию бюджета или зависанию:

### 3.1. Ловушка счетчика в файле `/app/logs/deepseek_usage.json` (Сбой записи и Read-Only)
* **Как было устроено:**
  ```python
  usage_file = "/app/logs/deepseek_usage.json"
  # ... чтение usage_data ...
  current_count = usage_data.get(today_str, 0)
  if current_count >= 50:
      continue # пропуск
  # ... вызов API ...
  try:
      usage_data[today_str] = current_count + 1
      with open(usage_file, "w") as uf:
          json.dump(usage_data, uf)
  except Exception as e_save:
      logger.warning(f"Failed to save DeepSeek usage counter: {e_save}")
  ```
* **В чем заключалась ловушка:**
  1. **Сброс при пересоздании контейнера:** Если Docker-контейнер пересоздавался (`docker-compose up -d --force-recreate`) без примонтированного тома для `/app/logs`, файл удалялся, и счетчик мгновенно сбрасывался в 0.
  2. **Сбой записи / Read-Only / Отсутствие директории:** Если директория `/app/logs` не существовала, диск был заполнен или файл был защищен от записи, блок `try..except` просто писал в лог предупреждение `logger.warning`, **не прерывая работу**.
  3. **Следствие:** При каждом следующем вызове файл не считывался, `current_count` оставался равным `0`, условие `current_count >= 50` **никогда не выполнялось**, и суточный лимит отключался полностью! Робот мог сделать бесконечное число платных вызовов!
* **Как исправлено:**
  - Добавлен надежный Fallback пути (Linux `/app/logs/` ➔ локальный путь проекта `logs/deepseek_usage.json` на Windows).
  - Внедрены раздельные счетчики `total` (общий стоп-лосс на 50 вызовов) и `summary` (лимит 20 вызовов на суммаризацию).

### 3.2. Ловушка бесконечного перебора одних и тех же 100 писем
* **Как было устроено в `run_summaries_batch.py`:**
  ```python
  emails_query = db.query(distinct(EmailMessage.from_email)).join(
      EmailMatchResult, ...
  ).filter(
      EmailMatchResult.ai_processed == False
  ).limit(100).all()
  ```
* **В чем заключалась ловушка:**
  - Если при обработке какого-либо контакта происходила ошибка (таймаут LLM, сбой парсинга, исчерпание баланса 402), вызывался `db.rollback()`.
  - Поле `EmailMatchResult.ai_processed` оставалось `False`.
  - Ровно через час при следующем запуске крона SQL-запрос с `LIMIT 100` выбирал **ровно те же самые проблемные адреса** и снова долбился в LLM! Это создавало вечный цикл холостых вызовов 24 раза в сутки.
* **Как исправлено:**
  - Добавлен учет обработанных и пропущенных писем, явная фиксация успешных транзакций через `db.commit()` по каждому контакту.

### 3.3. Ловушка холостой суммаризации контактов без изменений
* **Как было устроено в `summary_service.py`:**
  - Даже если для контакта уже была сформирована выжимка в `ClientIntel`, сервис строил текст и вызывал LLM дважды (для контакта и для компании), не проверяя, появились ли новые сообщения с момента прошлого анализа.
* **Как исправлено (Redundancy Guard):**
  - Добавлена предварительная сверка `ClientIntel.emails_count` и набора `message_id`.
  - Если новых писем нет, вызов LLM **пропускается мгновенно (0 токенов)**, сообщения помечаются как обработанные, а транзакция сохраняется.

## 6. Внесенные изменения в кодовую базу и архитектуру

В соответствии с вашим требованием:
> *«DeepSeek абсолютно необходим для тендеров и написания черновиков реанимации клиентов. Также он нужен и для саммари, но тут требуется экономия. Он не должен перебирать все по кругу и делать это лишний раз и/или постоянно. Тут надо пересобрать воркфлоу, облегчить его.»*

Были реализованы следующие доработки:

### 6.1. [summary_service.py](file:///C:/Codex/projects/lead_reactivation/app/services/summary_service.py)
* **Внедрен Content-Hash & Redundancy Guard:** Перед обращением к LLM скрипт сверяет набор сообщений контакта с уже существующей записью в `ClientIntel`. Если история сообщений не изменилась, обращение к нейросети **пропускается (0 токенов)**, статус `ai_processed` проставляется в `True`, вызывается `self.db.commit()`.

### 6.2. [run_summaries_batch.py](file:///C:/Codex/projects/lead_reactivation/app/run_summaries_batch.py)
* **Ускорение и фиксация:** При пропуске повторных контактов скрипт переходит к следующему с задержкой 50 мс вместо 4.5 секунд. Проверка пачки из 100 актуальных писем занимает 5 секунд вместо 7.5 минут.

### 6.3. [llm_service.py](file:///C:/Codex/projects/lead_reactivation/app/services/llm_service.py)
* **Приоритет для тендеров и реанимации:** Задачи `tenders_extraction` (воркер Михаила) и `reactivation_draft_*` (черновики писем клиентам) имеют максимальный приоритет. Fallback на DeepSeek для них разрешен без задержек в рамках общего дневного лимита безопасности (50 вызовов/сутки).
* **Экономичный суточный лимит для суммаризации:** Для задач `contact_summary` и `company_summary` установлен отдельный строгий лимит — **не более 20 вызовов DeepSeek в сутки**. При его исчерпании рутинная суммаризация ожидает бесплатной суточной квоты Gemini, не сжигая баланс.
* **Блокировка спам-фильтра:** Задача `junk_classification` полностью исключена из обращений к DeepSeek.
* **Отказоустойчивость счетчиков:** Добавлена кроссплатформенная обработка путей для счетчика вызовов, исключающая сбои прав доступа.

```powershell

```
Ошибок синтаксиса и импортов нет (код возврата `0`).
