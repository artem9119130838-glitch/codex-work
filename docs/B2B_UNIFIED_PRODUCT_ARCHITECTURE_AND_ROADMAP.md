# Единая платформа операционной эффективности и продаж (B2B AI Nexus)
## Архитектурный манифест, аудит инженерных гипотез, инвентаризация автоматизаций и пошаговый план MVP

> **Статус документа:** Архитектурная спецификация и дорожная карта продукта (MVP).  
> **Роли проекта:** Product Owner / Архитектор бизнес-процессов, Lead Backend / Инженер инфраструктуры.  
> **Область применения:** Тиражируемое On-Premise / SaaS решение для малого и среднего B2B-бизнеса (поставки оборудования, запчастей, материалов, ВЭД), использующего связку из 1С, CRM Битрикс24, корпоративной почты и облачной телефонии.

## 1. Разбор и оценка 10 инженерных предложений Lead Backend

Анализ гипотез перехода от прототипа к тиражируемому продукту. Инженерные решения одобрены по сути, но адаптированы под требования к ресурсам серверов малого бизнеса (экономия оперативной памяти и бюджета клиентов):

| № | Инженерная гипотеза | Оценка | Вердикт и адаптация под SMB | План реализации |
|---|---|---|---|---|
| **1** | **Гексагональная архитектура (отвязка от конкретной CRM)** | **10/10** | **Утверждается полностью.** Прямой хардкод методов Битрикс24 и ID полей блокирует масштабирование. Ядро должно оперировать событиями. | Внедрение интерфейса `ICRMAdapter` (`notify_manager`, `upsert_company`, `upsert_contact`, `create_activity`). Ядро публикует события (`LeadDiscovered`, `TenderParsed`, `FollowupDue`), адаптеры транслируют их в конкретную CRM. На этапе MVP — адаптер Битрикс24 и Mock-адаптер. |
| **2** | **Отказ от n8n в пользу собственного сервиса-координатора** | **9/10** | **Утверждается с заменой технологии.** Temporal избыточен для малого бизнеса (требует Cassandra/тяжелый Postgres, 4+ ГБ RAM). Клиенты не потянут его администрирование. | Замена n8n на компактный внутренний координатор **FastAPI + Celery / APScheduler / RabbitMQ Dispatcher** (потребление до 150 МБ RAM). Он автономно опрашивает почту IMAP, диски и 1С OData, раскладывая задачи в очереди. |
| **3** | **Миграции базы данных через Alembic** | **10/10** | **Обязательно для MVP.** Сырые SQL-дампы приводят к разрушению базы данных клиента при обновлениях версий. | Внедрение `Alembic` для PostgreSQL (pgvector + реляционная схема). Автоматический запуск `alembic upgrade head` при старте контейнера в `docker-entrypoint.sh`. |
| **4** | **Вынос аналитики в брокер и ClickHouse** | **7/10** | **Паттерн верен, хранилище скорректировано.** Отделять транзакции воркеров от аналитики необходимо, но ClickHouse для малого бизнеса (сотни документов в день) избыточен по RAM. | Воркер публикует легковесное событие `AnalyticsEvent` в RabbitMQ (`analytics_queue`). Фоновый сервис собирает батчи (по 50 записей или раз в 10 сек) и асинхронно сбрасывает в PostgreSQL. Архитектура готова к ClickHouse при росте нагрузки. |
| **5** | **Circuit Breaker для LLM и внешних API** | **10/10** | **Критично для всего контура.** Защищает не только балансы нейросетей, но и шлюзы 1С OData (при закрытии месяца) и телефонии. | Внедрение предохранителя (`pybreaker` / `tenacity`): при серии ошибок 429/503 шлюз встает на паузу (5–10 мин), задачи в очереди замораживаются. Сквозной **Multi-Tier Fallback**: Gemini $\to$ DeepSeek $\to$ локальная очередь. |
| **6** | **Bearer JWT вместо токенов в URL (`?auth=...`)** | **10/10** | **Стандарт безопасности.** Токены в query-параметрах оседают в логах Nginx и истории браузеров, что недопустимо при аудите безопасности B2B. | Перенос авторизации в заголовок `Authorization: Bearer <JWT>`. Middleware API Gateway проверяет токен до проброса запроса в локальную сеть. Входящие вебхуки валидируются через HMAC-SHA256 подпись. |
| **7** | **Монорепозиторий vs Независимый деплой** | **8/10** | **Разделение разработки и поставки.** Репозиторий остается единым для разработки, но клиент получает готовые закрытые контейнеры. | Настройка CI/CD в GitHub Actions: автоматическая сборка образов в GitHub Container Registry (GHCR). Клиент получает только `docker-compose.yml` и `.env`. Никаких `git pull` исходников у клиента (защита интеллектуальной собственности). |
| **8** | **Claim Check через MinIO/S3 для тяжелых файлов** | **10/10** | **Стандарт для документов.** Передавать файлы тендеров и сканы по 50–100 МБ через очередь RabbitMQ нельзя (риск падения сервера по OOM). | Развертывание локального контейнера `MinIO` (S3). Сервис сохраняет файл в бакет `raw-documents`, а в очередь отправляет только квитанцию: `{"claim_id": "...", "s3_uri": "s3://docs/doc1.pdf"}`. Воркер читает файл потоково. |
| **9** | **Распределенный трейсинг (OpenTelemetry + Jaeger)** | **9/10** | **Необходимо для технической поддержки.** Без сквозного ID расследование зависших документов у клиента занимает часы. | Сквозной `trace_id` генерируется на входе и передается через заголовки сообщений RabbitMQ во все воркеры и адаптеры. Инженер видит полный граф движения документа за секунды. |
| **10** | **Dead Letter Queue (DLQ / Карантин отравленных задач)** | **10/10** | **Отказоустойчивость.** Битые файлы или непредвиденные форматы не должны подвешивать конвейер в бесконечный retry-loop. | Настройка `x-dead-letter-exchange` в RabbitMQ. Сообщение после 3 неудачных попыток уходит в `quarantine_queue`. Конвейер продолжает работу, а администратор видит ошибку в панели управления. |

## 2. Полный обзор продукта и инвентаризация автоматизаций контура

Реальный B2B-бизнес работает в условиях технологического разрыва между системами. Продукт **B2B AI Nexus** ликвидирует этот разрыв, объединяя разрозненные каналы в сквозной конвейер.

```
                       ┌─────────────────────────────────────────────────────────┐
                       │                     ВХОДЯЩИЕ КАНАЛЫ                     │
                       │  IMAP Почта  │  АСТ ГОЗ / ЕИС  │  Новофон  │  Битрикс24 │
                       └────────────────────────────┬────────────────────────────┘
                                                    ▼
                       ┌─────────────────────────────────────────────────────────┐
                       │                   API GATEWAY & AUTH                    │
                       │     Bearer JWT Auth  │  Rate Limiter  │  OpenTelemetry  │
                       └──────────────┬───────────────────────────┬──────────────┘
                                      │ (Claim Check: файлы)       │ (События)
                                      ▼                           ▼
                       ┌─────────────────────────┐ ┌─────────────────────────────┐
                       │      MinIO Storage      │ │     RabbitMQ Event Bus      │
                       │ (PDF, DOCX, КП, Счета)  │ │   Queues + Dead Letter DLX  │
                       └──────────────┬──────────┘ └──────────────┬──────────────┘
                                      │                           │
                                      ▼                           ▼
                       ┌─────────────────────────────────────────────────────────┐
                       │                     ПУЛ ВОРКЕРОВ                        │
                       │  Тендерный RAG  │  Лиды & Скоринг  │ Follow-Up │ Аудит  │
                       └────────────────────────────┬────────────────────────────┘
                                                    ▼
                       ┌─────────────────────────────────────────────────────────┐
                       │               СЛОЙ АДАПТЕРОВ (HEXAGONAL)                │
                       │  ICRMAdapter   │   IERPAdapter    │ IPBXAdapter │  LLM  │
                       │  (Битрикс24)   │ (1С OData)       │  (Новофон)  │ (C.B.)│
                       └────────────────────────────┬────────────────────────────┘
                                                    ▼
                       ┌─────────────────────────────────────────────────────────┐
                       │            БАЗА ДАННЫХ (PostgreSQL + Alembic)           │
                       └─────────────────────────────────────────────────────────┘
```

### Реестр уже созданных и работающих автоматизаций контура:

1. **Модуль двухсторонней зеркальной синхронизации 1С и CRM (Mirror Sync):**
   * *Реализация:* Скрипты OData API (`Catalog_Контрагенты`, `Catalog_Лиды`, `Catalog_КонтактныеЛица`) для ERP (в контуре — 1С:УНФ, архитектурно любая 1С: 1С:УТ, 1С:ERP, а также МойСклад через `IERPAdapter`) и REST API для CRM (в контуре — Битрикс24, архитектурно любая: amoCRM, Мегаплан и др. через `ICRMAdapter`).
   * *Принцип:* **Идемпотентность и зеркальность**. Обновление в CRM зеркально обновляет 1С (через OData PATCH), и наоборот.
   * *Чистота данных:* Запрет на создание лишних пользовательских полей (`UF_*`), матчинг по ИНН и нормализованным контактам.
   * *Бизнес-ценность для компании/клиента:* Полная синхронность клиентской базы и реквизитов без ручного труда и без дорогостоящих 1С-программистов. Исключает человеческие ошибки менеджеров, задвоение контрагентов и путаницу в отгрузочных реквизитах, экономя компании до 20–30 рабочих часов в месяц.

2. **Модуль квалификации и скоринга контрагентов (Enrichment Engine):**
   * *Реализация:* Автономный скрипт опроса DaData API и сессионного парсинга СБИС (Saby) без дорогостоящего платного API.
   * *Функционал:* Подсчет точного количества участий в торгах в роли поставщика и заказчика.
   * *Тегирование:* Автоматическая классификация: `Перепродажник`, `Конечный покупатель`, `Производство`, `Тендер`, `Холдинг`.
   * *Бизнес-ценность для компании/клиента:* Моментальная квалификация входящего лида за 3 секунды. Менеджер сразу видит, с кем имеет дело: реальный ли это производственный завод или перепродажник-«пустышка». Это защищает маржинальность, отсекает неплатежеспособных контрагентов и экономит средства на платных тарифах сервисов проверки контрагентов.

3. **Модуль телефонии и адресной книги (PBX Sentinel):**
   * *Реализация:* Интеграция по протоколу JSON-RPC (в текущем контуре — АТС Новофон, архитектурно любая облачная или локальная телефония: Mango Office, UIS, Zadarma, Asterisk через `IPBXAdapter`).
   * *Стандарты:* Строгая нормализация телефонных номеров в формат `7XXXXXXXXXX` (без знака плюс), парсинг добавочных номеров из подписей писем в поле `patronymic` (`доб. 123`).
   * *Caller ID:* Синхронизация телефонной книги АТС — при входящем звонке менеджер сразу видит на экране имя компании из 1С и контактное лицо.
   * *Бизнес-ценность для компании/клиента:* Мгновенная идентификация клиента при входящем звонке и маршрутизация сразу на ответственного менеджера. Сокращает время удержания клиента на линии на 40%, повышает лояльность заказчиков («Здравствуйте! Звоните по поводу гидроцилиндров?») и исключает потерю звонков от ключевых покупателей.

4. **Автономный конвейер Follow-Up продаж (Sales Sentinel):**
   * *Реализация:* Скрипты мониторинга зависших сделок и дел в CRM (Битрикс24 / amoCRM).
   * *Функционал:* Сбор КП и спецификаций с диска с сохранением кириллических имен по RFC 2231, автоматическая генерация персонализированных черновиков писем через IMAP в почтовике менеджера (Roundcube `sales@...`).
   * *Дисциплина:* Защита от спама (кулдаун 7–10 дней), автоматический перенос дел `CRM_TODO` на +4..5 дней и эскалация в телефонный звонок при $\ge 2$ неотвеченных касаниях.
   * *Бизнес-ценность для компании/клиента:* Прямой рост выручки за счет дожима «зависших» сделок (+15–25% к конверсии коммерческих предложений). Менеджеры часто забывают повторно связаться с клиентом после отправки КП — система сама готовит индивидуальные черновики писем и контролирует дедлайны, не давая сделке остыть.

5. **Ликвидатор потери входящих писем (Inbound Mail Activity Sentinel):**
   * *Решение критического бага:* Устранение отрыва писем от существующих сделок при получении ответа с нового адреса клиента. Автоматическая привязка `CRM_EMAIL` к таймлайну сделки и патч контактных данных в 1С.
   * *Бизнес-ценность для компании/клиента:* Гарантированная защита от потери входящих писем и срыва переговоров. Если клиент пишет с нового личного ящика или от другого сотрудника, переписка никогда не потеряется и не создаст пустой дубль, а будет привязана к текущей сделке, предотвращая упущенную выгоду.

6. **Модуль реактивации спящей клиентской базы (Customer Reactivation):**
   * *Функционал:* Выгрузка из 1С клиентов, переставших покупать номенклатуру более 6 месяцев назад, генерация индивидуального коммерческого предложения на основе истории заказов и отправка персонального письма.
   * *Бизнес-ценность для компании/клиента:* Возврат ушедших клиентов с нулевой стоимостью привлечения (LTV booster). Вместо затрат на рекламу система находит клиентов, которые уже покупали определенные группы товаров, и делает адресное релевантное предложение, возвращая до 10–15% старой базы к регулярным закупкам.

7. **Тендерный RAG-пайплайн спецификаций (Tender Core):**
   * *Функционал:* Парсинг таблиц DOCX/PDF, опрос Белой базы векторных эмбеддингов, регуляторное сито ГОЗ (analytics sieve), расчет себестоимости.
   * *Бизнес-ценность для компании/клиента:* Сокращение времени первичного анализа тендерной документации с 2–4 часов до 30 секунд на лот. Исключает человеческий фактор при поиске номенклатуры в каталогах, автоматически выявляет регуляторные стоп-факторы (ГОЗ, нацрежим) и позволяет тендерному отделу обрабатывать в 5 раз больше заявок тем же составом.

8. **Операционный надзор, автогенерация регламентов и аттестация (HR & Operations Sentinel):**
   * *Функционал:* Сквозной сбор системных ошибок из чатов и задач CRM (Битрикс24), автоматическое формирование регламентов в Wiki и генерация проверочных экзаменов для сотрудников.
   * *Бизнес-ценность для компании/клиента:* Системная защита бизнеса от человеческого фактора и повторяющихся ошибок. Регламенты рождаются не из кабинетных фантазий, а из реальных косяков в чатах и задачах, а аттестационный экзамен гарантирует, что сотрудник понимает правила игры до допуска к клиентам и деньгам. Это снижает расходы на брак, штрафы и адаптацию новичков в 3–4 раза.

## 3. Архитектура 4 изолированных контуров («Порезка слона на бифштексы»)

Чтобы не допустить архитектурного коллапса при объединении сырых модулей, система делится на **4 автономных контура**. Каждый контур изолирован, имеет независимый цикл сборки и тестирования, и взаимодействует с другими только через брокер RabbitMQ.

```
┌─────────────────────────┐   ┌─────────────────────────┐   ┌─────────────────────────┐   ┌─────────────────────────┐
│        КОНТУР 1         │   │        КОНТУР 2         │   │        КОНТУР 3         │   │        КОНТУР 4         │
│      ТЕНДЕРНЫЙ RAG      │   │   ПРОДАЖИ И CRM SENTINEL│   │     1С:УНФ И СКОРИНГ    │   │      РЕГЛАМЕНТЫ И HR    │
│  (Lead Backend)         │   │   (Sales Core)          │   │   (ERP Core)            │   │   (Operations Core)     │
│ ─────────────────────── │   │ ─────────────────────── │   │ ─────────────────────── │   │ ─────────────────────── │
│ • Парсинг PDF/DOCX      │   │ • Follow-up черновики   │   │ • 1С OData (Read/Write) │   │ • Скан чатов и задач B24│
│ • Векторная база        │   │ • Новофон АТС (JSON-RPC)│   │ • DaData + Saby скоринг │   │ • База инцидентов и ТЗ  │
│ • Регуляторное сито     │   │ • Спасение писем        │   │ • Зеркальная база 1С/CRM│   │ • Авто-регламенты в Wiki│
│ • MinIO Claim Check     │   │ • Кулдаун касаний       │   │ • Реактивация базы      │   │ • Аттестационный экзамен│
│ • Alembic / DLQ         │   │ • Эскалация в звонки    │   │ • Контроль дебиторки    │   │ • Скоринг резюме соискат│
└─────────────────────────┘   └─────────────────────────┘   └─────────────────────────┘   └─────────────────────────┘
             │                             │                             │                             │
             └─────────────────────────────┼─────────────────────────────┴─────────────────────────────┘
                                           ▼
                       ┌───────────────────────────────────────┐
                       │     ЕДИНАЯ ШИНА СОБЫТИЙ (RABBITMQ)    │
                       │   Trace ID  │  Claim Check  │  DLQ    │
                       └───────────────────────────────────────┘
```

### Контур 1: Тендерный RAG и Спецификации
* **Зона ответственности:** Lead Backend.
* **Вход:** Ссылка на файл/извещение в MinIO (Claim Check).
* **Выход:** Стандартизированный JSON `TenderEvaluationReport`.
* **Изоляция:** Не зависит от наличия 1С или CRM. Тестируется на локальном каталоге тестовых документов.

### Контур 2: Продажи, Follow-Up и Телефония
* **Зона ответственности:** Product Owner / Sales Core.
* **Вход:** События CRM (просрочен дедлайн, входящий звонок, входящее письмо).
* **Выход:** Созданное дело, IMAP-черновик в Roundcube, всплывающая карточка в АТС.
* **Изоляция:** Работает автономным демоном, читая события из очередей `sales.inbound`.

### Контур 3: 1С:УНФ и Финансовый учет
* **Зона ответственности:** ERP Core.
* **Вход:** Данные контрагента (ИНН, реквизиты, заказы).
* **Выход:** OData PATCH/POST в 1С:УНФ, карточка благонадежности DaData/Saby.
* **Изоляция:** Защищен Circuit Breaker. Если 1С зависла на закрытии месяца — задачи накапливаются в очереди, остальные контуры не страдают.

### Контур 4: Операционный надзор, Регламенты и Аттестация
* **Зона ответственности:** Operations Core.
* **Вход:** Поток сообщений из рабочих чатов Битрикс24 и история выполнения задач.
* **Выход:** Автоматически сформированные регламенты в Базе Знаний Битрикс24, чек-листы и проверочные экзаменационные тесты.
* **Изоляция:** Работает как фоновый аналитический аудитор через REST API Битрикс24.

## 4. Сквозные инженерные стандарты на ВЕСЬ продукт

1. **Hexagonal Architecture (Слой адаптеров):**  
   Воркеры и бизнес-логика не содержат прямых вызовов конкретных вендоров. Все взаимодействия идут через интерфейсы `ICRMAdapter`, `IERPAdapter`, `IPBXAdapter`. Подмена систем не требует переписывания ядра.
2. **Claim Check Pattern (MinIO S3):**  
   Никаких бинарных файлов в очередях RabbitMQ. Сканы тендеров, вложения писем, файлы КП и счета сохраняются в локальное S3-хранилище. В шине передается только легковесный JSON-дескриптор с URI.
3. **Circuit Breaker:**  
   Единый механизм предохранителя для всех внешних шлюзов: LLM (Gemini $\to$ DeepSeek), 1C OData, DaData, Новофон. При серии ошибок шлюз временно размыкает цепь без потери сообщений.
4. **Dead Letter Queue (DLQ):**  
   Любое сообщение, вызвавшее сбой воркера более 3 раз, отправляется в карантинную очередь `dlq.*`. Система сохраняет 100% аптайм.
5. **Сквозной Trace ID (OpenTelemetry):**  
   Каждая входящая сущность маркируется уникальным `trace_id`, проходящим через все воркеры, логи и базы данных.

## 5. Реалистичная 5-этапная дорожная карта (Roadmap)

Вместо попытки слить все модули воедино за короткий срок, дорожная карта разбита на **автономные этапы** с независимой сдачей результатов.

### 🛡️ Принцип непрерывности бизнеса: Dual-Track Delivery (Параллельный саппорт и развитие)
Критическое требование к внедрению: **бизнес не останавливается ни на один день ради «великого рефакторинга»**.  
Все работы по созданию универсальных контуров идут строго параллельно с ежедневным саппортом и доработкой существующих боевых автоматизаций:
* **Трэк 1 (Бизнес / Саппорт):** Боевые скрипты прямо сейчас продолжают разбирать почту, квалифицировать контрагентов, слать follow-up черновики и синхронизировать 1С. Любые новые операционные требования бизнеса внедряются в них оперативно.
* **Трэк 2 (Платформа / Инженерия):** Разработчик параллельно строит надежный инженерный каркас (Alembic, MinIO Claim Check, брокер RabbitMQ, Circuit Breaker).
* **Синхронизация через Contract-First:** Контуры универсальности проектируются вокруг реальных форматов данных, которые уже крутятся в наших боевых скриптах. Если мы улучшаем боевую автоматизацию — мы просто обновляем контракт для шины событий. Ни переделка автоматизаций не тормозит создание платформы, ни разработка платформы не блокирует текущий бизнес.

```
[Этап 1: Стабилизация Контура 1 (Тендеры)] ──── 4–6 недель (Lead Backend)
[Этап 2: Автономизация Контуров 2 и 3 (CRM+1С)] ─ 4–5 недель (Параллельно)
[Этап 3: Запуск Контура 4 (Регламенты и Аудит)] ─ 3–4 недели
[Этап 4: Стыковка через шину RabbitMQ] ──────── 3–4 недели (Совместно)
[Этап 5: Упаковка в дистрибутив (Docker)] ───── 2–3 недели
```

### Этап 1. Стабилизация Контура 1 (Тендерный RAG) — 4–6 недель
* Внедрение `Alembic` для PostgreSQL;
* Развертывание `MinIO` и перевод парсеров на Claim Check;
* Перенос секретных ключей из URL в Bearer JWT;
* Настройка очередей RabbitMQ с Dead Letter Queue;
* Внедрение Circuit Breaker (Gemini $\to$ DeepSeek).
* *Критерий приемки:* Стабильная обработка пачки из 50 сложных документов без утечек памяти и зависаний.

### Этап 2. Автономизация Контуров 2 и 3 (CRM, 1С, Телефония) — 4–5 недель
* Упаковка Follow-Up конвейера и IMAP-черновиков в сервис `sales_sentinel`;
* Оформление синхронизации Новофон (JSON-RPC) в `PBXAdapter`;
* Оформление квалификации DaData/Saby в `EnrichmentAdapter`;
* Стандартизация OData-контрактов 1С:УНФ.
* *Критерий приемки:* Модули работают как надежные фоновые сервисы.

### Этап 3. Запуск Контура 4 (Регламенты, Аудит и Аттестация) — 3–4 недели
* Сканер чатов и задач Битрикс24 (выявление инцидентов, срывов дедлайнов, зависаний);
* Генератор регламентов и чек-листов с авто-публикацией в Базу Знаний Битрикс24;
* Модуль генерации аттестационных тестов (экзамен для сотрудников);
* RAG-скоринг резюме соискателей.
* *Критерий приемки:* Формирование регламентов на основе реальных ошибок сотрудников и автоматическая проверка знаний через тест в CRM.

### Этап 4. Стыковка контуров через Шину Событий — 3–4 недели
* Подключение адаптеров Контуров 1–4 к брокеру RabbitMQ;
* Сквозной трейсинг через OpenTelemetry (`trace_id`);
* Замена внешнего n8n на внутренний планировщик ядра.
* *Критерий приемки:* Сквозной прогон: тендер/письмо $\to$ скоринг $\to$ запись в 1С и CRM $\to$ Follow-Up дело $\to$ фиксация инцидентов.

### Этап 5. Упаковка в дистрибутив и релиз MVP — 2–3 недели
* GitHub Actions CI/CD: сборка закрытых Docker-образов в GHCR;
* Клиентский коробочный комплект: `docker-compose.yml`, `.env.example`, `install.sh`;
* Руководство администратора.
* *Критерий приемки:* Установка продукта на чистый сервер клиента одной командой за 15 минут.
